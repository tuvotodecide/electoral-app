# ADR-002: Validación de integridad del contador de intentos de PIN

## Decisión

Proteger el contador de intentos de PIN contra manipulación local mediante un **checksum SHA256** derivado del estado (intentos + lockout + salt), almacenado en SecureStore. Se valida antes de cada operación de login.

---

## Contexto

### Hallazgo de seguridad (MASVS-AUTH-4)
El contador de intentos fallidos se guardaba en **AsyncStorage sin encriptación ni validación**. Un atacante con acceso de raíz (root en Android, Jailbreak en iOS) podía:
1. Editar AsyncStorage y resetear el contador a 0
2. Reintentar el PIN offline sin límite de intentos
3. Bypassear completamente la defensa contra brute force

### Especificación del sistema
- **Requisito:** Detectar y bloquear si el contador fue alterado
- **Restricción:** Sin backend (es offline-first)
- **Restricción:** Debe ser rápido (una derivación criptográfica por validación)

### Modelo de amenaza
**Atacante:** Acceso al dispositivo con permisos de raíz  
**Objetivo:** Brute force del PIN  
**Línea de defensa:** Incremento de intentos + tiempo de espera (lockout)

---

## Alternativas consideradas

### 1. Validación en backend
```
Validar el contador en el servidor cada intento.

✅ VENTAJA: Más seguro (servidor es fuente de verdad)
❌ DESVENTAJA: Lento, requiere red, no es offline
❌ DESVENTAJA: No es compatible con arquitectura actual
```

### 2. Mover todo a Keychain
```
Guardar contador y lockout en SecureStore (Keychain/KeyStore).

✅ VENTAJA: Encriptado a nivel SO
❌ DESVENTAJA: Lento (io.crypto en cada validación)
❌ DESVENTAJA: Keychain también es accesible si atacante tiene el PIN
```

### 3. ✅ Checksum con SHA256 en SecureStore (ELEGIDO)
```
Guardar contador en AsyncStorage, checksum en SecureStore.
Checksum = SHA256(intentos + lockout + salt).

✅ VENTAJA: Rápido (una SHA256 por validación)
✅ VENTAJA: Si atacante altera AsyncStorage, el checksum no coincide
✅ VENTAJA: No requiere backend
✅ VENTAJA: Offline-first
```

### 4. HMAC con clave secreta
```
Usar HmacSHA256 con una clave inmutable en Keychain.

✅ VENTAJA: Más seguro teóricamente
❌ DESVENTAJA: Complejidad extra
❌ DESVENTAJA: Requiere generar/guardar clave en Keychain
❌ DESVENTAJA: Si atacante tiene Keychain, tiene todo (PIN + clave)
```

**Por qué se descartó HMAC:** La "clave secreta" en nuestro caso sería el PIN, que es mutable. Un HMAC real requeriría una clave distinta del PIN (lo cual agrega complejidad sin beneficio en este modelo de amenaza).

---

## Decisión técnica

### Flujo de registro (primera vez)
1. Usuario registra PIN "1234"
2. Generar salt aleatorio criptográfico = `SHA256(Math.random() + timestamp).substring(0,16)`
3. Guardar salt en SecureStore (SALT_KEY)
4. Guardar en AsyncStorage: `{KEY: "0", LOCK_KEY: null}`
5. Guardar en SecureStore: `{CHECKSUM_KEY: SHA256("attempts:0|lockUntil:null|salt:xyz")}`

### Flujo de login (validar)
1. Llamar `validateAttempts()` **ANTES de verificar PIN**
2. Leer checksum de SecureStore
3. Recalcular: `SHA256("attempts:N|lockUntil:null|salt:xyz")`
4. Si coinciden → integridad ok → proceder
5. Si NO coinciden → AsyncStorage fue alterado → resetear todo y bloquear

### Flujo de fallo PIN
1. Llamar `incAttempts()`
2. Calcular lockUntil (si intentos ≥ 5)
3. Recalcular checksum **CON el nuevo estado**
4. Guardar attempts + checksum de forma atomic
5. Próxima validación detectará si fue alterado

## Implementación

**Archivo:** `src/utils/PinAttempts.js`  
**Funciones principales:**
- `validateAttempts()` — Valida integridad antes de login
- `incAttempts()` — Incrementa y actualiza checksum
- `resetAttempts()` — Borra todo (intentos + checksum + salt)
- `getSalt()` — Genera/recupera salt con try/catch
